## Methods

**Setup.** MongoDB Community 9.0.8 arm64 (`mongod --version` v9.0.8, gitVersion 115a0fe2dcd8edd5bacd4557bd2e741a8e080665). Resolved as "latest stable" from `https://downloads.mongodb.org/current.json` (first entry, 9.0.8, `production_release: true`, base edition, macos/arm64); downloaded `https://fastdl.mongodb.org/osx/mongodb-macos-arm64-9.0.8.tgz`; sha256 `8e057ec463a52cfdea4b1b8f5d5108a622d9116dfff76332854b3627db772833` matches the sha256 published in current.json (verified). User-space, no sudo/Docker/Homebrew. Note: 9.0.8 was the first entry of current.json; whether MongoDB itself labels it "latest stable" beyond `production_release: true` is not independently checked. 3 × `mongod --replSet rs0 --bind_ip 127.0.0.1 --port {27017,27018,27019} --dbpath … --logpath … --logappend --pidfilepath …`. `--fork` is rejected on macOS ("incompatible with macOS"), so each mongod is started as a detached process (`start_new_session`); no other flags. Replica set initiated via pymongo `replSetInitiate` (3 members, default priority/votes). pymongo 4.18.3, Python 3.9.6 venv. Fresh topology per cell; persists across runs in a cell; each run uses a fresh collection and ID prefix; the victim is restarted after the window and the gate must pass before the next run.

**Defaults, as the running system reported (raw: `logs/defaults.txt`).**
- `electionTimeoutMillis` 10000, `heartbeatIntervalMillis` 2000, `heartbeatTimeoutSecs` 10, `catchUpTimeoutMillis` −1, `chainingAllowed` true; all members priority 1.0, votes 1; `writeConcernMajorityJournalDefault` true; `getLastErrorDefaults` `{w:1}` (legacy field).
- `getDefaultRWConcern` returned `defaultWriteConcern: {w: "majority", wtimeout: 0}`, `defaultWriteConcernSource: "implicit"`, `defaultReadConcern: {level: "local"}`. **So the system default write concern is w=majority** (implicit), and "acknowledged" in this study means acknowledged by a majority (2 of 3) with journaling. The driver itself sets no write concern (`client.write_concern == {}`), so the server's implicit default applies.
- pymongo: `retryWrites=True`, `retryReads=True`, driver-default `serverSelectionTimeoutMS` 30000, `heartbeatFrequencyMS` 10 s (as reported by the driver option object; I did not independently confirm the 10 s unit).

**Probe.** One writer thread, `insert_one` of `{_id, v, t}` into a per-run collection, via `mongodb://127.0.0.1:27017,127.0.0.1:27018,127.0.0.1:27019/?replicaSet=rs0` (driver discovers the primary; no hard-coded target). Write concern and `retryWrites` at defaults. **Instrument settings:** `serverSelectionTimeoutMS=2000` (driver default 30000), no socket timeout set. Target 200 inserts/s, **achieved about 100/s** (single sequential writer; median insert latency ~10 ms under w=majority with journaling), so the target is a ceiling, not what was delivered; acked per run ≈ 2,400 (M1) / 3,500 (M2). 5 s warm-up, kill, 30 s window. Every attempt logged (`runs/iter7-<cell>-rNN/probe.csv`: id, t_start, t_end, outcome, exception class). IDs `<cell>-rNN-<seq>`; a failed ID is never retried at application level; the writer moves to the next ID.

**Outcome classes (never merged).**
- `committed`: `insert_one` returned an acknowledgement.
- `failed`: `insert_one` raised after any driver-internal retry; ID not retried.
- `retryable_events`: count of `insert` command-failed events seen by a pymongo `CommandListener` during the run that were retry-eligible (error label `RetryableWriteError`, a NotPrimary-family code, or a network error with no server code). Attribution is per `_id` via the listener. In M1 every run had exactly 1 such event: the in-flight insert whose connection closed at the kill (`AutoReconnect` / connection closed or reset). In **all 30 runs that ID ended `failed`, not committed**: the driver retried once, server selection timed out after 2 s, and the application attempt failed. So `retried_then_committed` = 0 in this setup; the driver retry never succeeded because the election outlasted my 2 s selection timeout. Other failed attempts (110 total, 3.67/run) are `ServerSelectionTimeoutError` raised before any command was sent, so they produce no command event and are not counted as retryable events. A retried-then-committed write would count as committed, not lost or failed; none occurred. (Ambiguous results are possible in principle for the in-flight write: it may have committed but not been acked. That is not checked here as an "orphan" count; acked-lost only concerns acked IDs.)
- `acked_lost`: acked IDs absent from the post-settle primary, by querying every acked ID (`_id $in` batches of 1000) through a direct connection to the new primary, never inferred from probe logs.

**Metrics.** `kill_epoch` = instant before `kill -9 <pid>` of the victim (pid from `--pidfilepath`). `detect_s` = t_end of first failed attempt after kill − kill. `recover_s` = t_end of first committed attempt that started after the first failed attempt ended − kill. `write_stop_s` = (t_end of last commit before first failed attempt's start) − kill. First-failed-start→first-commit-end median 10.44 s [10.07–11.40] (notes column `firstfailstart_to_firstcommitend_s`; it differs from `recover_s` by −0.001 to +0.013 s per run because the first failed attempt starts at the kill). `max_gap_s` = largest gap between consecutive commit `t_end`s ending after the kill. `election_s` = kill → first `hello` reporting `isWritablePrimary` on a node other than `primary_before`, polled ~every 120 ms over direct connections to surviving nodes (observer worked in 30/30 M1 runs). `settle_s` = kill → health gate passing.

**Health gate (before each run and as "settled").** 3 mongod PIDs alive; `replSetGetStatus` shows exactly PRIMARY + 2 SECONDARY on two consecutive samples 0.5 s apart; an insert and a find through the replica-set client succeed; `optimeDate` lag ≤ 2 s (optimeDate has 1 s resolution, so an idle set legitimately reads 0–2 s; the residual lag at pass printed in the M1 notes column was 2.000 s in 25 runs, 1.000 s in 2 and 0.000 s in 3, which is an artifact of that resolution, not measured replication delay). Primary identified from `replSetGetStatus` through the replica-set client before the fault; M1 victim = primary, M2 victim = lowest-port secondary.

## Results

**M1 (N=30).** 30/30 `election`; new primary always differed. `recover_s` 10.45 [10.07–11.41]; `election_s` 10.50 [10.08–11.39]; `detect_s` 2.056 [2.042–2.066] (instrument-shaped, see above); `write_stop_s` 0.008 [−0.001–0.013] (writes stop at the kill); `max_gap_s` 10.44 [10.07–11.40]. Failed attempts 140 total (20 runs × 5, 10 runs × 4): 30 `AutoReconnect` (in-flight) + 110 `ServerSelectionTimeoutError`. Retryable events 30. Acked 73,031, lost 0. Old primary rejoined as secondary and gate passed in every run; no `no_recovery`, no rebuilds.

**M2 (N=15).** 15/15 `no_client_impact`: no failed attempt, no retryable event, 52,415 acked, 0 lost, largest commit gap ≤ 0.050 s. Primary stayed 27017.

**Smoke runs** (N=1 each, labelled, not counted): `results/smoke-M1.csv`, `smoke-M2.csv`.

## Cross-system placement

MongoDB M1 sits between CockroachDB and Redis Sentinel: a ~10.5 s client write outage that is essentially the shipped 10 s election timeout, longer than CRDB F1 (4.27 s) and tuned Patroni C3 (1.89 s), about half of Patroni C1 (22.38 s) and a third of Redis R1 (30.92 s). With the system default write concern recorded as w=majority, an acknowledged write is on at least two nodes, which is the plausible reason for 0 acked-lost (inferred, not tested; no w=1 comparison was run) versus PG C1's 2 async losses. The M2 control showed no client impact, like CRDB F2 and Redis R2.

Footnotes: (1) MongoDB is a document store; the probe is `insert_one`, not SQL INSERT. (2) The recorded default write concern is w=majority (implicit), so "acknowledged" means majority-acknowledged; acked-lost expectations differ from a w=1 system (Redis, async PG) and the 0 here must not be read as a like-for-like comparison. (3) MongoDB replication to secondaries is still asynchronous even with majority concern; majority acks mean at least one secondary has the write, not that all do. (4) Election timing follows the shipped `electionTimeoutMillis` (10 s) and does not map onto Patroni's TTL, CRDB's lease expiry or Sentinel's down-after. (5) Client paths differ: driver replica-set discovery vs Sentinel discovery vs multi-host libpq vs fixed gateway; and my 2 s `serverSelectionTimeoutMS` instrument shapes failed-attempt counts. (6) All single-host loopback. (7) Acked totals are not comparable across systems (different achieved rates and run lengths; MongoDB ~100/s achieved).

## Limitations

Single host, loopback, process kills only (no partitions, no disk faults, no load); one writer, small documents; defaults only (no w=1 or other write-concern comparison, no tuned election timeout); achieved write rate ~100/s, half the 200/s target; N=30/15 gives no meaningful tail percentiles; `serverSelectionTimeoutMS` 2000 ms is an instrument choice that sets the failed-attempt count and `detect_s` (the 10 s outage itself is election-bound); `election_s` has ~0.12 s polling granularity; replication lag readings are 1 s-resolution; only a primary-kill-with-restart pattern tested, not repeated kills inside a window. Loss of acked writes was not observed, which does not show it cannot happen. Why the in-flight write is never retried successfully (selection timeout < election time) is inferred from counts, not tested with a longer timeout.

## Anti-publication debate

**Debate (adversarial review session, 18 Nov 2026; full text `DEBATE-ITER7-AGAINST.md`):** verdict — include only with downgrades, NOT as a cross-system table row; MongoDB survives as one portability sentence, same tier as CRDB (iter 5) and Redis (iter 6). Central attacks: (1) "0 lost of 73,031" is not an exposure statement — only 16,131 acks (22.1%) preceded the kill and 19 came within 5 ms of it; at the implicit w=majority with optime-checked elections, loss from a single process kill is excluded by design, so the cell could not have produced a loss, and no w=1 or lag cell contrasts the guarantee with its absence. (2) The outage is the shipped 10 s election timer plus a residue (median 0.45 s [0.07–1.41]) that was never decomposed — and cannot be now: the per-cell fresh-topology rebuild deleted M1's mongod logs and data (logs/M1.log is 0 bytes), the same retention failure the Redis debate found. (3) The dominant client-visible failure mode is unmeasured and now unmeasurable: the 30 in-flight `AutoReconnect` writes were never checked for unacknowledged commits (CRDB's equivalent check found 29/30 had committed), because the M1 collections were wiped by the M2 rebuild; and the 2 s `serverSelectionTimeoutMS` made the driver's retryable-write path fail in 30/30 runs (`retried_then_committed` = 0), so the retryable class outcome is a joint property of MongoDB and the instrument — at the driver-default 30 s the in-flight write would very likely have been retried to a commit and the client would have seen one long blocked insert, not 4–5 failed attempts. (4) `detect_s` (2.056 s in every run) is the probe's own timeout; the 140 failed attempts are writer ticks of that 2 s timeout (runs with 5 failed attempts: median recover 10.58; with 4: 10.12). (5) `election_s` and `recover_s` are the same event seen twice (recover − election negative in 26/30 runs, mean −0.046 s, observer poll ~120 ms); election_s's only added value is showing the delay is server-side. (6) M2's victim was always 27018 and the primary always 27017 — the control never rotated. (7) The writer achieved ~100 inserts/s (latency-bound under w=majority journaling), so lag/loss at real write rates is untested. (8) "Latest stable" rests only on being the first entry of current.json — all eight listed versions carry identical production/current/LTS flags. (9) The cross-system table is becoming a catalogue of shipped timer defaults (Patroni TTL 30, Sentinel down-after 30 s, MongoDB election 10 s, CRDB lease) with no mechanism or loss analysis around this one.

**Adjudication (Muse, director):** I recomputed the debate's checkable claims from the raw CSVs and per-run probe logs BEFORE adjudicating: recover − election negative in exactly 26/30 runs, mean −0.046, range −0.107 to +0.019; residue over 10 s median 0.452 [0.074–1.409]; failed-attempt groups 5× (n=20, median 10.578) vs 4× (n=10, median 10.123); at-risk set exactly 16,131 pre-kill acks of 73,031, 19 within 5 ms and 160 within 50 ms of the kill; logs/M1.log is 0 bytes; all eight current.json versions carry the same three flags — all match the debate exactly. ACCEPTED IN FULL: the verdict (include only with downgrades, no table row) and all eight required changes, including the debate's exact one-sentence paper wording (election timeout 10000 ms + median residue 0.45 s as the lead figure, not "10.45 s"; at-risk denominator 16,131 / 19-within-5 ms replacing "0 of 73,031" in any comparative use; the 2 s selection timeout and `retried_then_committed` = 0 stated wherever the client experience is described; in-flight writes marked unchecked; version labelled "MongoDB 9.0.8, first entry of current.json, sha256-verified"; M1 log/data non-retention stated; M2 fixed-victim wording; ~100/s achieved rate next to every loss claim).
