## 2. Methods

**Install.** Official MySQL Community Server 8.4.13 LTS, `mysql-8.4.13-macos15-arm64.tar.gz` from `cdn.mysql.com/Downloads/MySQL-8.4/`, user space under `tools/`, no sudo/Docker/Homebrew. Release resolved from the `dev.mysql.com/downloads/mysql/` page, which lists two LTS lines (9.7.4 and 8.4.13); I chose 8.4.13 as the long-established GR line. Not tested on 9.7. MD5 `73926da59774274b5cdfe78cd2150840` is published on `dev.mysql.com/downloads/mysql/8.4.html` and matches the downloaded file (verified; GPG signature not checked). `mysqld --version`: `8.4.13 for macos15 on arm64 (MySQL Community Server - GPL)`. Driver: `mysql-connector-python` 9.4.0 (pure-Python mode) in `~/tools/venv`.

**Topology.** 3 instances on 127.0.0.1: MySQL ports 3310/3311/3312, GR `local_address` 33161/33162/33163, `group_seeds` all three, `server_id` 1/2/3, single-primary mode, XCom communication stack. Separate datadir, socket, pid and error log per instance under `data/<cell>/mN/`. m1 bootstrapped, m2 and m3 joined by incremental distributed recovery from a binlog donor (the default path; the clone plugin is not loaded). No Router. Fresh topology per cell (G1: `data/G1`, G2: `data/G2`); within a cell the topology persists across runs, each run uses a fresh table (`lab.t_<cell>_<run>`).

**Required-for-GR vs tuning.**
- Required (set): distinct `server_id`; `gtid_mode=ON`; `enforce_gtid_consistency=ON`; `log_bin` with `binlog_format=ROW`; `group_replication_group_name` (one UUID); `group_replication_local_address`/`group_seeds`; plugin load; recovery user `rpl_user` with REPLICATION SLAVE, CONNECTION_ADMIN, BACKUP_ADMIN, GROUP_REPLICATION_STREAM; `group_replication_bootstrap_group=ON` on m1 only for the first START; `mysqlx=OFF`, `report_host=127.0.0.1`, `bind-address=127.0.0.1` (plumbing). One authentication prerequisite: `group_replication_recovery_get_public_key=ON`, because the recovery user uses `caching_sha2_password` over a non-SSL channel (without it members stuck in RECOVERING; the `CHANGE REPLICATION SOURCE … GET_SOURCE_PUBLIC_KEY=1` form was rejected on the GR channel with error 3139).
- Build-time only override: the three instances were first booted with `--group_replication_start_on_boot=OFF` so my explicit START/bootstrap did not race the auto-start. Restarts after a kill use the shipped default; `@@group_replication_start_on_boot` = 1 on a restarted member (checked on G2 m2). The captured `logs/defaults.txt` shows OFF for m1 for that reason (m1 was never restarted before capture).
- Everything else is at default. No tuning of consistency, member weight, exit-state action, flow control, transaction-size limit, expel or election timeouts.

**Defaults as reported by the running system** (`logs/defaults.txt` for G1, `logs/defaults-G2.txt` for G2; they differ only in member UUIDs and group name): `group_replication_single_primary_mode=ON`, `group_replication_enforce_update_everywhere_checks=OFF`, `group_replication_consistency=BEFORE_ON_PRIMARY_FAILOVER`, `group_replication_exit_state_action=OFFLINE_MODE`, `group_replication_member_expel_timeout=5`, `group_replication_unreachable_majority_timeout=0`, `group_replication_autorejoin_tries=3`, `group_replication_flow_control_mode=QUOTA` (applier/certifier thresholds 25000), `group_replication_member_weight=50`, `group_replication_transaction_size_limit=150000000`, `gtid_mode=ON`, `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`, `binlog_format=ROW`, `replica_parallel_workers=4`, `replica_preserve_commit_order=ON`. `transaction_write_set_extraction` and `binlog_transaction_dependency_tracking` are not reported by `SHOW VARIABLES` on 8.4.13, so I have no value for them. `performance_schema.replication_group_members` at capture: 3 ONLINE, 3310 PRIMARY, 3311/3312 SECONDARY, version 8.4.13.

**Probe** (`bin/harness.py`). One writer thread; each attempt is one `INSERT` in one autocommit transaction of `(id, ts)` with `id = <cell>-r<run>-<seq>`; a failed ID is never retried (the writer moves to the next ID). Target 200 writes/s; **achieved about 165/s before the kill** (single sequential writer, certification latency; median per cell 164.5 G1, 164.7 G2). Every attempt is logged (`id,t_start,t_end,outcome,errno,err,port`) in `runs/iter8-<cell>-rNN/probe.csv`.

*Client path (caveat, no Router):* the probe resolves the primary itself. When it has no connection it connects to each member in port order (3310, 3311, 3312), reads `performance_schema.replication_group_members`, and connects to the member that is `PRIMARY` and `ONLINE`; if none is, the attempt fails with a client-side `RuntimeError('no_primary')` (logged errno 0). Any error drops the connection, forcing a fresh resolution on the next attempt. The resolution time is inside the attempt. This is not driver replica-set discovery, not Sentinel and not a gateway; it is my own loop and it shapes failed-attempt counts.

*Instrument settings:* `connection_timeout` 2 s (applies to connect and statement socket operations, pure-Python connector), 1 s timeout for the group-view query; 0.1 s sleep after every failed attempt (so failed attempts are about 7–10/s during an outage, not unbounded); warm-up 3 s plus uniform 0–1 s jitter before the kill; after the kill the probe runs at least 20 s and until the first clean commit (hard cap 90 s, never reached); the victim is restarted only after the window. Observer: separate thread, polls `replication_group_members` through each surviving member every 0.15 s over persistent connections.

**Health gate** (before every fault and as "settled"): all 3 mysqld pids alive; two samples 0.5 s apart each show 3 ONLINE, exactly 1 PRIMARY and 2 SECONDARY and are identical; an insert + select round trip through the primary; on each secondary `COUNT_TRANSACTIONS_IN_QUEUE = 0`, `COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE = 0` and `GTID_SUBSET(primary gtid_executed, own gtid_executed) = 1`. Timeout 150 s; failure would be `no_recovery`. It never failed. Run-end per-member row counts were also recorded and equal in every run (`notes`, `ledger.json`).

**Faults.** `primary_before` is read from `replication_group_members` through a surviving connection before injecting. G1 victim = the primary; G2 victim = the lowest-port secondary (always 3311; primary stayed 3310 in all 15). `kill_epoch` = `time.time()` immediately before `kill -9 <pid from pid file>` of that instance only. Restart is by `bin/topo.sh start` (same config, default start_on_boot).

**Metrics.** `detect_s` = end of first failed attempt after the kill − kill (that attempt may have started before the kill). `recover_s` = end of first committed attempt that started after that failed attempt ended − kill; the first-failed-start→first-commit-end duration is in `notes` (`ffstart_to_commit_s`, G1 median 21.49 [21.04–22.12], within 0.01 s of `recover_s`). `write_stop_s` = end of the last commit that ended before the first post-kill failure − kill (G1 −0.00 [−0.01–0.00]: writes stop at the kill). `max_gap_s` = largest gap between consecutive commit ends where the later one ends after the kill. `election_s` = kill → first observer sample in which a member other than `primary_before` reports PRIMARY. `settle_s` = kill → health gate passing.

**Outcome classes (never merged).** `committed` = the INSERT returned without error. `failed` = the attempt raised. `retryable` = a failed attempt whose error is in the primary-change/connection family: errno 1290, 1180, 1205, 1213, 3100, 2013, 2006, 2055, 2003, −1 (connector OperationalError, connection lost mid-statement), or errno 0 (my own `no_primary` or timeout classes). Attribution is by error code only; it is coarse, because during a primary kill every failed attempt is primary-change-related, so retryable = failed in G1. Observed codes in G1 (totals over 30 runs): `no_primary` 3,458; 2003 connection refused 1,152; −1 24; 2013 lost connection 5; 2055 1. None of 1290/1180/1205/1213/3100 occurred. `retried_then_committed`: not measured: the driver does no internal retry and the application never retries an ID, so it is 0 by construction. `unacked_present` = failed IDs that are present on the new primary after settle. `acked_lost` = acked IDs absent from it.

**Reconciliation.** After settle, the full table of IDs is read from the new primary (`SELECT id`) and every acked and failed ID is checked by set membership against it; that is a full-ledger comparison, not inferred from probe logs.

## 3. Results

### G1 — `kill -9` the primary (N=30)
- 30/30 `election`; every run elected a different primary. Primary alternated between exactly 3310 and 3311 (15× 3310→3311, 15× 3311→3310); 3312 was never elected in these 30 runs (no reason established; it is the highest port).
- `recover_s` 21.49 [21.05–22.12], mean 21.54. `election_s` 21.48 [21.07–22.09]. Per-run difference election − recover ranged −0.14 to +0.08 s; negative values are the observer's 0.15 s poll granularity.
- `detect_s` 0.03 [0.03–0.03]: the kill gives immediate connection errors, so the client fails at once but cannot write until the view change. `max_gap_s` 21.49 [21.05–22.13]. Failed attempts 4,640 (151–163 per run); retryable 4,640 (same set).
- Acked 18,012 (median 605/run), pre-kill 17,432. **Acked-lost 0.** The `consistency=BEFORE_ON_PRIMARY_FAILOVER` default makes the new primary hold new transactions until it has applied its backlog; this did not add a visible delay beyond the view change (no failure other than the connection/no-primary class), but I did not isolate it.
- `unacked_present` 3 (runs 8, 12, 20; one ID each): an INSERT in flight at the kill returned a connection error (e.g. run 8: errno 2013 "Lost connection to MySQL server during query") yet the row was present on the new primary. These are counted as `failed`, not acked-lost.
- Old primary restarted and rejoined as a secondary in every run; no `no_recovery`, no rebuild. All three members held identical row counts at the end of each run.

### G2 — `kill -9` secondary (N=15)
- 15/15 `no_client_impact` (zero failed attempts, zero retryable). Victim always 3311; primary 3310 throughout. Acked 9,970; lost 0; `unacked_present` 0.
- Degraded write path while the dead member is still in the view: see §1 (about 4 commits/s, each about 0.247 s [0.24–0.257], for the whole 20 s window; clears at about kill+21 s per the diagnostic run). Because the window was 20 s, the victim was restarted at about the moment GR removes it; the G2 `settle_s` therefore includes a 30.17–39.41 s spread (14 of 15 within 30.17–32.51 s).
- Smoke runs (N=1 each, labelled, excluded): `results/iter8-smoke-G1.csv` (run smoke1; run before the retryable set gained 2003/−1, so its retryable count differs) and `results/iter8-smoke-G2.csv`. Diagnostic run: `runs/iter8-G2-diag01` (not in any CSV).

## 4. Anomalies and honest gaps
- `election_s` is blank in G1 runs 11, 14, 19, 27. Harness race: the probe's first commit on the new primary arrived just before the observer's next poll and the harness stopped the observer once the probe had recovered; the observer's last sample still showed the old primary UNREACHABLE. Not substituted with `recover_s`.
- The 5.4 s / 16 s split between "unreachable" and "removed" comes from member error logs of the smoke run and run logs under `data/G1/m2/error.log`, `data/G1/m3/error.log`. I did not test why removal takes about 21 s in total (the shipped `member_expel_timeout` is 5); I report timing only.
- Which port wins the election (never 3312) is observed, not explained.

Footnotes (caveats):
1. **Replication model.** GR certifies a transaction by group quorum agreement on its writeset before it commits, so an acknowledged write has been agreed by a majority. Async PG/Redis can ack before any replica has the write. The loss expectation differs fundamentally; the "0 lost" in G1 must not be read as a like-for-like comparison with PG C1 or Redis R1. It is also not a claim that GR cannot lose acked writes under other faults (partitions, disk loss, force-quorum) which were not tested.
2. **Failure detection is not comparable.** GR detection is membership/view-change based; it does not map onto Patroni's TTL, CockroachDB's lease expiry, Sentinel's down-after or MongoDB's election timeout.
3. **Client paths differ:** probe-side primary resolution here (no Router) vs driver replica-set discovery (MongoDB) vs Sentinel discovery (Redis) vs multi-host libpq (PG) vs fixed gateway (CRDB). My failed-attempt counts depend on a 0.1 s failure backoff and 2 s timeout.
4. Everything is single-host loopback, process faults only, one writer.
5. The controls are not equivalent: G2's lack of failed attempts hides a large throughput collapse; the other controls' max commit gaps were ≤0.07 s.

## 6. Limitations
Single host, loopback, no network latency; `kill -9` process faults only (no partition, disk, or clock faults); one sequential writer with small single-row transactions (about 165/s achieved against a 200/s target); shipped defaults only (plus GR prerequisites), so nothing here says what a tuned GR would do; MySQL 8.4.13 only (9.7.4 LTS was available and not tested); no Router; N=30/15 gives no meaningful tail percentiles; the group never lost quorum (2 of 3 survivors). The primary role rotated between only two members in G1.

## Anti-publication debate

**Debate (adversarial review session, 18 Nov 2026; full text `DEBATE-ITER8-AGAINST.md`):** verdict — include only with downgrades, NOT as a cross-system table row; MySQL survives as one portability sentence, same tier as CRDB (iter 5), Redis (iter 6) and MongoDB (iter 7). Central attacks: (1) The G1 outage is a membership constant — and the write-up UNDER-claimed: the retained server logs decompose all 30 runs (the write-up said the split was "observed once" in the smoke run): kill → survivors log "unreachable" at a median 5.39 s [5.01–5.99]; unreachable → removal a near-constant 16.00 s later [16.000–16.934]; removal → the probe's first commit a median 0.08 s [0.02–0.15]. So N=30 measured ~1 s of detection jitter around two constants, and the dominant 16 s phase is unexplained — the shipped `group_replication_member_expel_timeout` is 5 s and does not give 16; "set by membership failure detection" labels only the first 5.4 s. (2) "0 lost" is design-excluded: GR certifies by group quorum before commit, so a single primary kill with two survivors cannot lose a certified write; no loss-capable cell (partition, second fault, quorum loss) was run, and the table cell must carry the at-risk denominator (17,432; 28 within 5 ms) plus the cannot-produce-loss qualifier, not "0 of 18,012". (3) The retryable class is empty: retryable = failed by construction, 74.5% of failures are the probe's own errno-0 `no_primary`, `retried_then_committed` is 0 by construction — and the write-up's claim that failed counts depend on a 2 s timeout is WRONG: no failed attempt in G1 lasted more than 0.051 s, so the count (~155/run) is purely the probe's 0.139 s tick; what IS a MySQL property is the timing of the error-class switch (2003 while the dead member still shows ONLINE PRIMARY, then `no_primary` after "unreachable"), which readouts the two phases. (4) `election_s` is `recover_s` seen through a 0.15 s poll and is blank in 4/30 runs (observer stopped at probe recovery; verified in the observer files) — the log-based removal time replaces it with no gaps. (5) 3312 was never elected, likely by construction: server UUIDs on disk are ordered m1 (522adafe…) < m2 (53e56c9c…) < m3 (56556504…), and at equal version and member_weight (all 50) the lowest UUID is believed to win (debate flags this as from memory, not docs-checked) — so G1 covers 2 of 3 possible primaries by construction. (6) G2, the slice's only novel phenomenon, is real but thinner than stated: per-commit latency went 1.8 ms → 0.247 s ±2 ms (137×; 1,233 post-kill commits, 15/15 runs) — the write-up's "from about 6 ms" is wrong (6 ms is write spacing, not latency) and its certification-latency explanation of the 165/s ceiling fails at 1.8 ms commits; the probe/connector path is excluded as cause (same connection, 1.8 ms before, 247 ms after), flow-control QUOTA looks unlikely (thresholds 25,000, queues empty at the gate) but was not sampled during the window; the clearing at removal (~21.8 s) is seen in exactly ONE diagnostic run — in all 15 counted runs the probe window ended at 20.0–20.5 s, before the earliest logged removal (21.2 s), and in 6 counted runs the victim rejoined before any removal was logged; and the CSV outcome label `no_client_impact` misleads for a latency-visible fault with zero failed attempts — the honest class is throughput/latency degradation, which is exactly the client class an error-count probe cannot see, and the best instrument lesson in the slice. (7) Attacks on magnitude fail: probe rediscovery + the `BEFORE_ON_PRIMARY_FAILOVER` hold together are ≤0.15 s (removal → first commit), so the no-Router client path and the consistency default cannot explain the 21.49 s; they survive only as scope limits (Router's own cache refresh untested; the hold under a lagging secondary untested). (8) Exposure attack mostly fails: at-risk 17,432 (28 ≤5 ms) is comparable to MongoDB's 16,131 (19 ≤5 ms); the smaller total is because writes stop for 21.5 s of each ~25 s run. (9) Version label: "MySQL 8.4.13 LTS (one of two current LTS lines; 9.7.4 not tested; MD5-verified, signature unchecked)".
